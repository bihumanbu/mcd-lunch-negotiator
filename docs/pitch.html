WALL 01

一单只能挂一张券

7 个人合并成一单，等于白扔 6 张券。所以团队点餐本质是拆单， 不是推荐。

WALL 02

券绑在个人账户上

账号不能跨人共享。所以正确形态是一个人算、每人自己扫， 而不是一个人替全组付款。

每单支付链接 15 分钟有效 → 所以一个人连扫 5 单来不及， 链接要分给各自扫。

为什么不是「又一个点单工具」

单点推荐是用乘法，拼单是用组合。

一单只能挂一张券、且券归属不同的人时，「怎么分单」的解空间比「每顿吃什么」大得多—— 7 个人、5 种可用券、一单一张，拆法有几十种，每种省钱效果都不一样，而且必须用官方计价接口验证。

GitHub 上已有 100+ 个麦当劳 MCP 项目，几乎全部是单人视角（帮我一个人省钱、算卡路里）。 团队拼单这个角度，还没人做。

踩到的坑（比功能更能说明做了什么）

套餐专属 SKU 单点返回 0，不是报错
「可乐中杯」不单卖，calculate-price 返回 0。 直接把 0 当免费求和，会把「套餐省多少」算成荒谬值（¥35 的套餐单点只要 ¥13.50）。 现改为同档位可单点商品做保守下限估值，并在输出里逐条标注。
批量计价遇到无效 SKU，整单归零
14 个商品里混进一个非卖品，price 直接返回 0， 不报错。必须逐个校验再合并。
参数约束没写在 schema 里
query-nearby-stores 在 searchType=2 时， city 和 keyword 必须同时传，只传一个报 600058。
单位方向相反
计价返回「分」（2790 = ¥27.90），菜单和订单返回「元」字符串。 混用一次，全部金额差 100 倍。
响应不是纯 JSON
同一套接口返回三种形态：「字段说明书 + 原始 JSON」混合文本、Markdown 表格、 TOON 文本。不写解析层，一行数据都取不出来。
支付窗口 15 分钟，推翻了原设计
下单实测：payH5Url 真实存在，但 expirePayTime 只有 15 分钟。5 张订单一个人连扫来不及——所以「一个人替全组付款」不成立， 改成「一个人算，每人自己扫」。

边界与安全

不做

不做自动支付。只算方案 + 生成支付链接，付款由人扫码。 写操作失控是这类工具最大的风险点。

不做

不管理多账户 Token。券绑个人账户，跨账户在规则和技术上都不成立， 产品定位是「一个人的账号替全组算账」。
